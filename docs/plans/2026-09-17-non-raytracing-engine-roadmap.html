一、当前基线与规划结论

v0.1.0 已经具备完整的静态渲染骨架：Deferred PBR、方向光与 CSM、IBL、SSAO、SSR、后处理、Terrain、Atmosphere、Water、Volumetric Clouds、God Rays、ECS、场景加载、编辑器层级和 Inspector。下一阶段的目标不是继续无限打磨单个屏幕空间算法，而是扩大引擎能制作的内容类型。

现有能力当前事实对路线的影响
光照场景配置已有 lights: Vec 和 Point / Spot 类型，但运行时实际主要消费第一个方向光。多光源是现成数据模型上的高收益补全，第一版局部光不做阴影。
材质普通物体主要支持颜色、粗糙度、金属度和 Albedo 纹理；Terrain / Water 已有更丰富的纹理路径。先把 Normal、ORM、Emissive 补到普通物体，复用已有纹理缓存。
透明Water 是专用 Forward Pass，通用透明物体、玻璃和粒子还没有统一入口。建立窄接口的单层透明 Pass，暂不引入 OIT。
编辑器已有层级、选择、删除、Undo/Redo、Inspector 和基础实体创建。优先补复制、重命名、创建灯光和组件操作，投入小、内容生产收益大。
运行时physics_system 目前是占位实现，模型加载以静态网格为主。物理先于动画；动画以 glTF + 单角色播放为第一切片。

T2 多光源运行时 P0

接口与数据结构

enum LocalLightKind { Point, Spot }
struct LocalLight {
    kind: LocalLightKind,
    position: Vec3,
    direction: Vec3,
    color: Vec3,
    intensity: f32,
    range: f32,
    inner_cos: f32,
    outer_cos: f32,
}
struct LightingFrame {
    sun: DirectionalLight,
    locals: Arc<[LocalLight]>,
}

保留现有方向光和 CSM 作为唯一阴影光源。局部光限制为 32 个，按 Entity bits 稳定排序并截断；超出数量只记录 warning，不改变场景加载结果。

技术实现

  1. Scene Loader 不再只取 lights.first()，区分 Directional 和 Local lights。
  2. RenderFrame 传递不可变的 LightingFrame。
  3. LightingPass 使用 Storage Buffer 上传局部光。
  4. WGSL 实现 point 距离衰减和 spot cone 衰减。
  5. 保留 8 个 SSAO/CSM/IBL 方向光变体，局部光在变体内部累加。
  6. 第一版局部光不投影、不参与水面反射重渲染。

测试与验收

  • CPU 单测：衰减、spot cone、零范围、32 个上限、稳定排序。
  • Shader parse / bind layout 测试。
  • 专项场景：红/绿/蓝三点光 + 一个 Spot + 一个方向光。
  • HTML 报告确认光色、衰减、材质响应和方向光阴影没有消失。

风险控制

不在第一版做局部阴影，避免把 CSM 复杂度复制到 Point / Spot。Storage Buffer 不暴露给场景文件，只由 Frame 层管理容量。若性能低于目标，先降低上限，不改变接口。

T3 普通物体 PBR 材质增强 P0

接口与数据结构

扩展 MaterialConfig，保持旧 RON 默认值兼容：

normal_texture: Option<String>
metallic_roughness_texture: Option<String>
occlusion_texture: Option<String>
emissive: [f32; 3]
emissive_texture: Option<String>

材质加载得到内部 MaterialTextureSet，纹理句柄和 fallback 由 AssetManager / TextureCache 管理；GBuffer 和 Lighting 不直接读取场景文件。

技术实现

  1. 扩展材质配置、默认值和序列化。
  2. 扩展材质批处理 key，避免不同纹理错误合批。
  3. GBuffer 使用切线空间 Normal Map。
  4. Lighting 读取 ORM / AO，并加入 Emissive。
  5. 缺失纹理使用稳定 fallback，不在生产路径新增 unwrap。
  6. Inspector 支持数值和路径编辑。

测试与验收

  • RON 默认值和 round-trip 单测。
  • 材质批处理 key 的纹理隔离测试。
  • Shader parse 和 uniform layout 测试。
  • 专项场景：法线砖块、金属粗糙度排布、发光物体。
  • HTML 对比确认普通物体视觉变化，旧场景无意外变暗。

范围边界

Alpha Mode 不在 T3 实现，留给 T4。第一版不做材质图形节点、不做运行时 shader permutation 爆炸；使用固定纹理槽和 fallback。

T4 通用透明 Forward Pass P1

接口与资源（摘要）

引入 TransparentRenderItem 和 TransparentBlendMode { Alpha, Additive }。Pass 读取真实存在的 GDepth / SceneColor，写入独立的 TransparentColor，最后由 Composite 统一混合，避免直接读写同一 SceneColor；完整资源顺序见 T4.1。

透明对象按相机空间深度从后到前排序；深度测试开启、深度写入关闭。第一版只保证单层排序透明。

实现任务

  1. 从普通物体中分离透明 render item。
  2. 建立透明材质和 blend state。
  3. 实现深度排序和空输出清理。
  4. 将透明输出接入 Composite。
  5. Water 保留专用波浪/折射逻辑，不在本任务强行迁移。
  6. 验证窗口 resize、场景切换和无透明物体路径。

测试与验收

  • 排序函数和 blend 配置单测。
  • 资源表签名、空透明输出、场景切换测试。
  • 专项场景：玻璃平面、Alpha 物体、Additive 发光体。
  • HTML 截图确认透明物体和不透明物体深度关系正确。

明确不做

不做 OIT、深度剥离、多个透明层的物理正确排序、透明物体投射阴影、通用折射。需要这些能力时另开 T4.2。

4.5.1 统一时间控制合同

enum TimeMode { WallClock, FixedStep, Seek }
struct TimeControl {
    mode: TimeMode,
    simulation_time: f32,
    fixed_dt: f32,       // default 1.0 / 60.0
    max_substeps: u32,   // default 4
    frame_index: u64,
}
struct TimeSample { time: f32, dt: f32, step_index: u64 }

impl TimeControl {
    fn advance(&mut self, wall_dt: f32) -> Result<SmallVec<[TimeSample; 4]>, TimeError>;
    fn seek(&mut self, target: f32) -> Result<(), TimeError>;
    fn reset(&mut self) -> Result<(), TimeError>;
}
模式语义各动态系统行为测试
WallClock正常交互；wall_dt 经 clamp 后进入 accumulator。Physics 按 fixed_dt 子步；Particle 按同一 TimeSample；Animator 使用 sample.time。暂停/恢复、max_substeps、丢帧 clamp；不得超过 4 个子步。
FixedStep每帧恰好一个固定 dt，适合 replay。所有系统只消费同一个 step_index，禁止各自读取 Instant。同 seed/同初始场景 replay 的状态 hash 一致。
Seekreset scene/runtime 后从初始状态按 fixed_dt 重建到目标时间；目标必须是 fixed_dt 的整数倍，否则返回 TimeError::NotOnStep。Physics 重放 n steps；Particle 用 step_index spawn；Animator 直接采样 time；禁止依赖 wall clock。0、0.5、1.0 秒重复 seek 得到同一 state hash；负数/NaN/超时错误明确。

CLI 合同为 --time-mode wall-clock|fixed-step|seek、--simulation-time <seconds>、--fixed-dt <seconds>、--max-substeps <n>。现有 --freeze-time 暂时是 seek 0.0 的兼容别名，并在报告中标记 deprecated；所有截图 case 必须显式写 time mode，不能依赖默认值。

4.6.3 T0/T1：验证和编辑器实现闭合

T0.2 明确实现为一个长期存活的 runner 进程、每次只有一个无 GUI 的 launcher child；runner 不持有 Metal，当前 launcher child 独占一个 Metal device/session，case 按 manifest 顺序串行执行，child 结束后才进入下一个 case；不会为 case 创建 Terminal，也不会并发打开多个 launcher。每个 case 的 argv 固定为 [launcher_binary, "--scene", case.scene] + case.launcher_args + ["--no-gui-overlay"]，runner 通过 pipe/文件 descriptor 将 stdout/stderr 分别绑定到 case 目录，launcher.log 记录 argv、pid、pgid、start/end、exit/signal、device metadata。ProcessGroupSupervisor 在 spawn 前为本次 case 创建 ProvisionalLease{nonce,expected_binary,state=Reserved}；child 在 exec 前调用 setpgid(0,0)，runner 立即把 pid、OS start-time 和 pgid 绑定进该 lease，再等待一字节 ready handshake。只有 supervisor 将 lease 状态从 Bound 原子推进到 Ready 后，runner 才开始 handshake_timeout=2s 之后的 case 计时；因此 handshake 超时仍有一个 supervisor-owned、已绑定身份的 provisional lease 可清理。supervisor 是唯一拥有 lease 和终止能力的常驻 helper：它在 lease 有效期内原子执行 identity-bound group cleanup，先 SIGTERM、最多等待 5s 再 SIGKILL，随后确认 group 为空；runner 不直接调用裸 killpg，也不通过递归扫描 child PID 清理。parent 的 setpgid(child_pid,child_pid) 仅作为创建阶段的幂等竞态收敛，不能替代 supervisor lease；PID、start-time、pgid 和 nonce 必须在同一 supervisor 请求中重新校验，校验失败返回 ProcessIsolationLost 且禁止扩大到未知进程。spawn 失败在 lease 尚未绑定时只撤销 provisional lease；bind 失败先关闭 handshake pipe，再由 supervisor 按已绑定身份清理；handshake 超时进入 ChildHandshakeTimeout 并由 supervisor 清理。平台不支持 process-group setup 时在创建 child 前返回 UnsupportedProcessIsolation，不启动 launcher，不改写 report。每 case timeout=120s；EXIT/INT/TERM 都执行一次可重入 cleanup，lease 丢失则只记录诊断并 fail closed。日志和产物路径固定为 tests/reports/<run-id>/<case-id>/{stdout,stderr,launcher.log,graph.txt,reference.png,output.png,diff.png}。fake-process test 必须验证 orphan descendant、handshake timeout、runner signal、重复 cleanup、case 间残留、PID reuse/race、lease loss、spawn/bind failure 和 supervisor 等待 group 为空；清理完成前不得开始下一个 case。

计时边界固定且不允许双重等待：handshake_deadline 从 child spawn/bind 完成时开始，长度为 2s；runner 在收到 ready byte 后立即把 lease 推到 Ready，取消 handshake timer，并以 t_ready 作为 case duration 的起点。每 case 的 120s hard timeout 是 t_now - t_ready，不是 spawn 到 now，也不是在 Ready 后再额外等待 2s；handshake 未在 2s 内 Ready 直接返回 ChildHandshakeTimeout 并进入 cleanup。cleanup 时间不延长下一 case 的启动条件，只有确认 group 为空后才允许继续。

4.6.11 开工单固定格式、追踪与状态

每个 slice 开工单必须从 register 和 primary case 生成，不允许只写“实现功能”。固定字段为：目标与用户收益、当前代码事实、修改文件、唯一 Seam、数据/接口/所有权/错误合同、实现任务序列、单元/接口/集成/专项测试、primary case id、variant matrix、依赖与人日、primary/backup assignee、feature flag、fallback、退出条件、提交 hash 和 HTML 报告路径。实现状态只允许 planned → in_progress → verified → released；测试失败进入 blocked 并保留产物，不能通过改阈值或删除 case 转为 verified。

#[serde(tag = "type")]
enum ExitPredicate {
    CommandPass { command: String, exit_code: i32 },
    VisualAggregatePass { report: PathBuf, variants: Vec<VariantExit>,
        relations: Vec<VariantRelation>, #[serde(default)] paired: Option<PairedRunRelation> },
    ExpectedDiagnostic { report: PathBuf, variant: String, code: String },
    MetricGuard { report: PathBuf, expression: String },
}
struct VariantExit { id: String, expected: ExpectedResult }
struct VariantRelation { name: String, variants: Vec<String>, rule: String }
struct PairedRunRelation { baseline_label: String, feature_label: String,
    rule: String, same_device_key: bool, same_pair_key: bool }
struct SliceExitContract { predicates: Vec<ExitPredicate>, artifacts: Vec<PathBuf>,
    forbidden_states: Vec<String> }
// serde uses the lower-case `type` discriminator and the JSONL below is the exact serialized shape.
// Every register row must expand its prose exit into this machine-readable contract.

每个 slice 的退出条件必须至少包含一个 CommandPass、一个与 primary case（及其所有 variants）对应的 VisualAggregatePass/ExpectedDiagnostic 或明确的 fixture 结果，以及 stdout/stderr/launcher.log、HTML、PNG/JSON、graph/metrics dump 中适用的 artifact；forbidden_states 至少包含残留进程、stale generation、未处理 error 或 needs-review。这样“通过”“回退”“预期错误”都成为可解析状态，不用定性文字替代。

状态变更必须具备的证据禁止行为
planned → in_progress本轮独立评分全部 ≥9.5，依赖已满足，primary case 和 fallback 已登记。评分未通过时提前写生产实现或把历史草案当规范。
in_progress → verified改动对应的 unit/interface/integration test、专项 HTML/PNG、日志和 graph/metrics dump 齐全。只以编译成功或“截图看起来差不多”作为证据。
verified → released相关版本 gate、CI、module health、受影响场景 regression 和 commit 记录全部通过。把研究项结果伪装成 release feature，或无记录地扩大范围。

七、评分协议与迭代规则

独立 reviewer agent 必须对整份文档、每个 T0–T9 父任务和全部 33 个 slice 分别评分，不以“总体感觉不错”代替逐项评分。每个对象按固定的 V/A/I/E/C/T/G/D 八个维度各 10 分，满分 80；评分说明必须指出低分原因和具体改文建议。T8.4 及 T9.4 虽属于可回退/研究切片，仍必须达到同一评分门槛，不能以“不阻塞版本”抵消规划缺口。

评分维度满分标准
V — 价值/优先级能解释为什么现在做、能带来什么可见或可用收益，并且没有把低收益工作提前。
A — 架构/Seam模块职责清楚，接口窄而深，调用者不需要知道实现细节，和现有 RenderFrame / Pass / ECS 能自然衔接。
I — 接口/所有权有可落地的类型/函数签名、所有权、生命周期、容量、序列化和线程约束；接口隐藏实现细节且支持未来 adapter。
E — 错误处理错误类型、来源、传播、可观测诊断和局部回退明确；错误不会被静默吞掉，也不会污染已发布状态。
C — 任务与范围完整性从数据、运行时、渲染、编辑器、序列化到文档均有任务，没有隐藏的大块工作；第一版边界明确。
T — 测试可执行性同时覆盖单元、接口、集成和专项视觉验证，case/variant、输入、阈值、失败产物和 HTML 证据路径均可执行。
G — 发布/回退门禁feature flag、发布条件、版本兼容、失败回退、阻塞规则和 release evidence 都可机器判定。
D — 排期/依赖/资源先后顺序、跨 slice 依赖、owner、容量、并行关系和超时重排规则显式且可追踪。
最终状态规则：只要 reviewer 对整份文档、任一 T0–T9 父任务或任一 33 个 slice 的 V/A/I/E/C/T/G/D 任一项给出低于 9.5，文档保持 Draft；先更新技术设计、拆分任务或补测试，再重新评分。全部对象的全部维度均达到 9.5 以上后，状态才改为 Implementation Ready。总分/平均分不能抵消任何单项低分。
